사용자 근거: `Q1 A / Q2 A / Q3 A / Q4 A / Q5 A`, “추천해 준 A안을 모두 채택하겠습니다.” 후속 요청으로 P2 하네스 문서를 작성했다. 오늘의 상한은 P2이며 P3~P5와 앱 기능 구현은 진행하지 않는다. 이 문서는 당시 선택지·답변 이력이며 확정 정책의 상세 기준은 [ADR 목록](decisions/README.md)이다.

제안서에서 이미 정한 Python 3.11, 로컬 실행 우선, Streamlit·PyMuPDF·LangChain·LangGraph·Chroma·OpenAI SDK·python-dotenv와 우선 검토 모델은 다시 묻지 않는다. 근거는 [프로젝트 브리프](project-brief.md)와 [제안서 원문](<../PDF 기반 AI 학습 도우미 — RAG 기반 질의응답·요약·문서 비교 시스템>)을 참고한다.

## Q1. 의존성·개발 검사 도구는 어떤 방식으로 관리할까요?

근거: 제안서 §4.3은 Python 3.11 가상환경과 라이브러리를 명시하지만 패키지 관리자·잠금·검사 도구는 정하지 않았다. 현재 관련 파일도 없다.

- **A — uv + pyproject.toml/uv.lock + Ruff·pytest (추천):** 잠금 파일과 환경 동기화로 재현하기 쉽다. uv라는 추가 도구를 익혀야 한다. Python 3.11을 고정하고 향후 검증 명령을 통일하기 좋아 추천한다.
- **B — venv + pip/pip-tools + Ruff·pytest:** 표준 가상환경과 pip에 익숙하면 접근이 쉽다. 잠금 생성·환경 동기화 절차를 별도로 관리해야 한다.
- **C — venv + pip와 최소 의존성 목록만 먼저 구성:** 시작은 단순하지만 잠금·자동 검사의 재현성이 약해 후속 정리가 필요하다.

pytest 선택은 향후 의미 있는 테스트를 둘 도구 결정이며 이번 단계에서 테스트나 앱 코드를 작성한다는 뜻은 아니다.

## Q2. 초기 테스트 PDF는 어떤 자료로 준비할까요?

근거: 제안서 §6은 공개·사용 허가 PDF 또는 개인 학습자료를 계획하지만 실제 자료와 라이선스를 정하지 않았다. §3.1 목표는 텍스트 추출 가능한 PDF 3개 이상이다.

- **A — 직접 만든 비민감 텍스트 PDF 3개부터 사용 (추천):** 권리·내용·정답을 통제하기 쉽다. 실제 강의자료의 복잡성은 덜 반영한다. 초기 검증과 출처 기록을 단순하게 시작할 수 있어 추천한다.
- **B — 공개 자료 중 사용·외부 처리 조건을 확인한 PDF 3개:** 현실적인 자료로 검증 가능하지만 출처·라이선스·이용조건 확인이 필요하다. 선택 시 자료 링크 또는 식별 정보를 답변에 적는다.
- **C — 사용자가 지정한 개인 학습자료:** 실제 수요에 가깝지만 저작권·개인정보·외부 전송 허용 여부를 먼저 확인해야 한다. 선택 시 사용 가능한 자료 범주를 적는다.

## Q3. OpenAI API로 보낼 수 있는 자료 범위는 어디까지인가요?

근거: 제안서 §3.1·§4.2의 임베딩·LLM 처리는 문서 텍스트와 질문 등의 외부 전송을 수반하지만 §6은 전송 허용 범위를 정하지 않았다. Q2의 자료 선택과 별개로 확인이 필요하다.

- **A — Q2 자료 중 권리·전송 허용을 확인한 비민감 샘플만 허용 (추천):** 계획된 OpenAI 구조를 검증하면서 노출 범위를 제한한다. 개인 자료의 실제 사용 검증은 뒤로 미뤄진다. 초기 데이터 정책을 명확히 할 수 있어 추천한다.
- **B — 개인정보를 제거하고 전송 권한을 확인한 개인 학습자료까지 허용:** 실제 사용에 가깝지만 익명화 검토와 권리 확인 부담이 있다.
- **C — 당분간 외부 전송 금지:** 로컬 문서·정적 검사 및 향후 대체 응답 검증부터 준비할 수 있다. OpenAI 임베딩·생성의 실제 검증은 보류되며, 로컬 모델 전환은 별도 범위 결정이 필요하다.

## Q4. API 비용과 키 관리 책임은 어떻게 정할까요?

근거: 제안서 §4.1은 호출량 산정 예시와 구현 전 공식 요금 확인을 제시하지만 실제 예산·결제 계정 담당자·초과 시 동작을 정하지 않았다. 지금 키 값을 보내지 않는다.

- **A — 초기 유료 호출 0원, 사용자 관리 키를 나중에 연결 (추천):** 비용 없이 하네스를 먼저 정리할 수 있다. 실제 API 연동 검증은 이후에 해야 한다. 현재 초기 문서화 단계에 적합해 추천한다.
- **B — 사용자 관리 계정으로 소액 한도 내 실호출 허용:** 실제 연동 검증이 가능하지만 비용이 발생한다. 선택 시 예산 금액·통화·적용 기간과 관리자를 적는다. 이후 하네스에서 한도 도달 시 호출 중단 기준을 구체화한다.
- **C — 학교/팀 제공 계정 사용:** 공동 결제 관리가 가능하지만 사용 승인·키 전달 방식·한도 담당자 확인이 필요하다. 선택 시 사용 가능 여부와 한도 정책을 적는다.

어느 선택도 지금 유료 호출을 승인하거나 키를 요청하는 절차가 아니다. 실제 연동 전 당시 공식 가격과 설정을 확인해야 한다.

## Q5. 로컬 문서·임베딩·대화/평가 기록은 얼마나 보관할까요?

근거: 제안서 §3.1은 Chroma 저장, §4.1은 임베딩 재사용을 계획하지만 저장 경로·보관 기간·삭제 정책은 없다.

- **A — 개발 PC에 원본·추출문·Chroma를 Git 제외 경로로 보관하고 개발 종료 시 삭제, 비민감 평가 결과만 별도 기록 (추천):** 임베딩 재사용으로 비용을 줄이며 저장소 노출을 제한한다. 종료 시 원본과 파생 자료를 함께 삭제하는 절차가 필요하다. 제안서의 재사용 계획과 초기 로컬 환경에 맞아 추천한다.
- **B — 매 세션 종료 시 원본·파생 자료·대화 내용 삭제:** 잔존 데이터를 줄인다. 세션 간 임베딩 재사용이 어려워 비용·처리 시간이 늘 수 있다.
- **C — 사용자가 정한 경로·기간으로 보관:** 학교/개인 정책에 맞출 수 있다. 별도 설정이 필요하다. 선택 시 경로와 기간, 로그에 질문·답변 본문을 남겨도 되는지 적는다.

API 키는 어느 경우에도 저장소에 넣지 않고, 테스트 PDF의 저장소 포함 여부는 Q2의 권리 확인 후 별도로 구분한다.
